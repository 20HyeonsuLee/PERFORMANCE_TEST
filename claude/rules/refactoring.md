# 리팩터링 규칙 (rules/refactoring.md)

## 1. 리팩터링의 전제 조건
- **테스트 코드 확인:** 리팩터링 전 반드시 해당 로직을 검증하는 테스트 코드가 존재해야 한다. 테스트가 없다면 테스트 먼저 작성한다.
- **기능 변경 금지:** 리팩터링 단계에서는 외부로 드러나는 동작(비즈니스 로직)을 절대 변경하지 않는다.

## 2. 주요 코드 스멜(Code Smells) 및 해결책
- **긴 메서드 (Long Method):** 메서드가 15줄을 넘어가면 논리적 단위로 분리하여 메서드를 추출(Extract Method)하라.
- **거대한 서비스 (Large Service):** 서비스 계층에 비즈니스 로직이 몰려 있다면, 이를 엔티티 내부로 옮겨라 (Domain Logic Migration).
- **데이터 클래스:** 로직 없이 필드만 있는 클래스는 '객체지향 생활체조' 원칙에 따라 기능을 부여하거나 VO로 전환하라.
- **중복 코드:** 유사한 로직이 2군데 이상 나타나면 공통 유틸리티나 부모 클래스, 또는 컴포넌트로 분리하라.

## 3. Java/Spring 특화 리팩터링
- **Legacy Loop -> Stream:** 전통적인 `for/while` 루프를 Java Stream API로 전환하여 가독성을 높여라.
- **Imperative -> Functional:** 복잡한 조건문 중첩은 `Optional`과 `Lambda`를 활용하여 선언적인 코드로 개편하라.
- **의존성 정리:** 사용하지 않는 주입(Bean)이나 불필요한 필드를 제거하고, 생성자 주입 방식이 아닐 경우 생성자 주입으로 교체하라.

## 4. 리팩터링 절차
1. 코드 스멜을 식별하고 사용자에게 개선 방향을 먼저 제안한다.
2. 작은 단위로 리팩터링을 수행한다 (한 번에 너무 많은 것을 바꾸지 마라).
3. 리팩터링 후 반드시 테스트를 실행하여 기존 기능이 깨지지 않았음을 증명한다.
